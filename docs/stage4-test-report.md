# 阶段 4 测试报告

> 历史合成实验记录：下文测试和环境属于原注明的受测版本，不是本候选重新执行结果。原 Git 历史未随快照提供；当前候选资源名/端口及验证状态以 README 和 candidate-validation.md 为准。

执行日期：2026-10-15（Asia/Shanghai）

环境：Windows amd64、Go 1.27.2、Docker Engine 29.8.2、MySQL 8.4.12。集成测试只使用随机命名的 `order_api_it_*` 临时数据库。

## 自动化验证

以下命令实际执行成功：

```powershell
gofmt -w .
go mod verify
go vet ./...
go test -count=1 ./...
go vet -tags=integration ./...
.\scripts\test-integration.ps1
```

单元测试覆盖输入规范化、与顺序无关的摘要、请求限制、领域错误到 HTTP 的映射、金额乘法边界、MySQL 错误码分类、1213/1205 有限重试、重试上限和取消停止。

MySQL 集成测试实际验证：

- 单商品与多商品创建、总金额、SKU/名称/价格快照。
- 商品不存在、停用、库存不足和金额上限失败时不残留订单。
- 后续商品库存不足时，前一商品的已执行扣减回滚。
- 通过测试库触发器注入订单明细写入错误后，订单头和库存整体回滚。
- 相同键相同请求返回同一订单；不同请求返回 409；商品输入顺序不影响摘要。
- 12 个相同幂等键并发请求最终只有 1 个订单、1 个明细并仅扣减一次。
- 12 个不同键并发争抢 5 件库存，最终 5 单成功、7 单库存不足、库存为 0，订单和明细各 5 条。

真实死锁不是稳定、可重复的集成测试条件。本阶段使用可控的 `MySQLError` 1213/1205 单元测试验证完整事务重试与次数限制，没有把它描述成真实数据库死锁测试。

## 实际开发库 HTTP 冒烟验证

使用键 `stage4-real-20261015-1228` 对商品 1 创建数量 1 的订单：首次 HTTP 201，订单总额 5999 分，开发库存从 50 变为 49；相同请求重放 HTTP 200 且订单 ID 不变；同键数量改为 2 返回 HTTP 409。数据库查询确认只有 1 个订单头和 1 个订单项。
