## 执行方式与停止条件

先完成 5 秒、5/s 冒烟，再执行每场景 300 秒固定到达率，最大 25 VU。每轮有独立 5 秒预热、正式窗口、结束一致性验证和 30 秒负载后观察。资源与结果稳定后，在最终修复版本上单独将单热点延长为600秒。采样使用 k6 内部正式时钟；约 301.8 秒宿主 wall time 包含启动及监测收尾，数据重置、迁移、预热和 cooldown 不计入 k6 的正式分位数。

阈值为 HTTP 错误率小于 1%、P95 小于 1 秒，15 秒后允许提前停止；检查失败、非预期业务响应、dropped iteration 均使该轮失败。脚本可用 `.tmp/stability/STOP` 或前台中断停止。进程 working set 超过 512 MiB、表/索引分配估计超过 1 GiB、可用盘低于 20 GiB、监测失败或时间超限时停止。磁盘保护是检测与停止条件，不是宿主 Volume 的物理配额。

每 5 秒尽力保存一次聚合样本，共 244 个样本；Docker 命令耗时使实际采样时间有所偏离，CSV 保存实际 UTC。每分钟 k6 子指标保存真实分位数，不采用“平均各分钟 P99”计算整轮 P99。事务分段为整轮分布；HTTP/service/transaction/SQL 时间互相嵌套，不相加。

## 正确性、问题与复现

每轮 `perf-verify` 均确认无负库存、金额不一致、无明细订单、孤立明细和重复用户级幂等。写入增量与成功响应一致；80/20 和单热点还执行了逐商品库存守恒校验，差异均为 0。恢复套件另覆盖授权、取消回补与逐商品校验。

修复两个启动脚本问题：`/health` 返回顶层 `status`，原脚本错读 `data.status`；资源 override 应在应用连接池启动前应用，否则容器重建会让第一次 warm-up 遇到旧连接。这两次初始化失败不计入正式结果。故障发现及错误分类修复见 [恢复报告](failure-recovery-report.md)。

命令与资源边界见 [测试入口](../tests/stability/README.md)。轻量数据为 `tests/stability/results/stability-summary.json`、`stability-runs.csv`、`stability-windows.csv` 和 `stability-monitor.csv`；大体积或含本地 Session 的材料留在忽略的 `.tmp`。

本地实验支持“上述版本在四个指定5分钟场景及最终版本10分钟单热点场景中通过了检查”，不支持“无内存泄漏”“生产最大容量”“多节点容灾”或“已解决所有P99问题”。后续应在明确资源预算后复现末端延迟变化，再考虑更长期的独占环境验证；本阶段没有引入 Redis 的充分证据。
