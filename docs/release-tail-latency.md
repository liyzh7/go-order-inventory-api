# 发布候选版：限时尾延迟复核

> 历史合成实验记录：下文测试和环境属于原注明的受测版本，不是本候选重新执行结果。原 Git 历史未随快照提供；当前候选资源名/端口及验证状态以 README 和 candidate-validation.md 为准。

2026-10-17，本阶段只补充两轮各 600 秒正式采样，现已结束，不无限延长调查。阶段 9/10 的数据、报告和迁移未覆盖。

## 版本与方法

- 应用：干净 HEAD `a3e41576be6029f637f45195c1e3dc33ad983ef0` 构建，二进制 SHA-256 `b593dc4c67c19e24ac43f6a05a37d59b804079be10c82080767040e91d4ad211`；两轮使用同一进程/二进制。新增验收文件没有混入正在测量的二进制。
- Windows 11 / Ryzen 7 8845H，Go 1.27.2，k6 2.3.0，Docker MySQL 8.4.12，沿用 2 CPU/2 GiB、256 MiB buffer pool、256 MiB redo 容量上限。完整参数见 `tests/release/results/tail-environment.json` 及阶段 10 环境记录。
- 独立 `order_api_perf_baseline`，每轮重置为等价的固定种子、1,000 商品、25 用户/Session，每商品 1,000,000 库存，不修改开发库。
- 固定到达率 50/s、最多 25 VU、请求超时 3 秒；5 秒预热另算，正式 600 秒、30 秒冷却。先以 5/s、5 秒冒烟，26 次请求且守恒通过。
- 资源每 5 秒采样。仅第二轮额外每 15 秒读取 COMMIT/redo/文件 IO 累计计数；从约第 51 秒起有完整相邻区间，不能用作第一分钟完整指标。没有重置 Performance Schema，也没有同时执行迁移、备份或其他压测。

两轮期间进行了轻量源码/文档审查和个别短工具测试，未隔离所有宿主后台任务；因此不是无干扰物理机实验。第二轮辅助观察调用约 0.2 秒/次（含 Docker exec 往返），可能有额外开销，不把两轮小差异当 A/B 优化收益。

## 资源、锁与 COMMIT 证据

| 指标 | r1 | r2 |
| --- | ---: | ---: |
| Go 平均使用 CPU 核数 | 0.0915 | 0.0838 |
| 最大 working set / heap | 52.53 / 35.31 MiB | 32.96 / 14.63 MiB |
| goroutine 峰值 / 冷却后 | 55 / 18 | 42 / 15 |
| 冷却后池 in-use / idle | 0 / 10 | 0 / 7 |
| 池等待增量 | 0 | 0 |
| GC 次数 / 累计暂停增量 | 140 / 4.23 ms | 143 / 4.23 ms |
| 行锁等待次数 / 累加等待增量 | 144 / 5,711 ms | 137 / 3,516 ms |
| 成功事务 P95 | 18.67 ms | 18.95 ms |
| COMMIT P95（整轮 Go 诊断） | 10.58 ms | 11.08 ms |

累计行锁时间是所有等待的总和，不是单请求延迟。两轮没有死锁、锁超时或事务重试；各轮库存/订单/明细增加量严格对应 30,001 个成功请求，逐商品守恒及所有业务不变量通过。

阶段 10 最后两分钟 heap 没有单调增加，连接池无等待；本轮冷却后无在用连接，goroutine 回到与空闲连接数相符的水平。第二轮复用同一应用进程仍未出现持续积累证据，不能据此断言“内存泄漏”，也不能证明任意时长永不泄漏。

第二轮辅助采样中，末段相邻 15 秒区间 COMMIT 平均耗时约 8.66～10.89 ms。按实际 COMMIT 次数加权：结束时间不晚于 480 秒的已覆盖区间为 **4.96 ms / 21,297 次**；开始时间不早于 480 秒的区间为 **9.92 ms / 5,323 次**（跨界区间单独排除）。这提供了末段 COMMIT 变慢的相关证据，**不是 COMMIT 分钟 P95/P99**。

同一覆盖区间 redo checkpoint age 从约 3.2 MB 增至约 16.3 MB，`Innodb_log_waits` 与 `Innodb_buffer_pool_wait_free` 增量均为 0；远低于配置的 256 MiB redo 容量不等于不存在存储同步/后台刷盘影响。文件等待计数包含后台线程，不能全部归属到某条业务 SQL，也不能与嵌套事务时长直接相加。

没有获取宿主 SSD 队列/同步刷盘尾延迟、虚拟化调度的可归因跟踪，也没有每分钟事务阶段分位数。现有证据支持“末段延迟上升与 COMMIT/存储路径时间变化相关”，不足以区分 WSL/宿主 IO、后台刷盘、热表增长或其他环境因素，更不能把 COMMIT 认定为唯一根因。

## 处理决定与限制

没有确认可安全修复的核心算法缺陷，因此不为尾延迟盲目改事务、连接池、索引或一致性约束，不增加 Redis。保留为已知性能风险；本地 50/s 无错误且守恒通过不等于生产 SLO/容量已验收。

逐分钟完整数据、资源样本与辅助计数区间保存在 `tests/release/results/tail-*.json/csv`。阶段 10 的原始分钟数据仍在原目录，本阶段另生成只读复核摘要 `stage10-tail-review.json`。后续如继续调查，应单独授权在无干扰 Linux/明确磁盘指标环境复测，不将这次两轮自然波动冒充优化收益。
