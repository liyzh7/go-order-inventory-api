# 阶段 8 性能基线

> 历史合成实验记录：下文测试和环境属于原注明的受测版本，不是本候选重新执行结果。原 Git 历史未随快照提供；当前候选资源名/端口及验证状态以 README 和 candidate-validation.md 为准。

日期：2026-10-16（Asia/Shanghai）。这是本机、回环网络、短时合成负载下的比较基线，不是生产容量承诺。测试期间没有修改业务实现、事务隔离、数据库约束或索引。

## 隔离数据与安全边界

种子为 `20261016`，每次显式重置生成 1000 个商品、25 个合成用户及 Session、500 个一商品待取消订单。商品 1 有 100 件竞争库存，其他商品初始库存 1,000,000；预创建订单会同步扣减相应库存。用户名、商品和 Token 均由性能命令生成，不含真实个人资料或开发凭据。

`cmd/perf-seed` 同时要求 `-allow-reset`、精确 `-expected-database`，并校验实际库名匹配 `^order_api_perf_[a-z0-9_]+$`，否则拒绝删除或插入。Token 只输出到忽略的 `.tmp/performance/manifest.json`，k6 结果和提交文件不含 Token。密码哈希保留安全随机盐；影响工作负载选择的数据和 Token 由固定种子确定。

服务运行时诊断只有显式 `DIAGNOSTICS_ENABLED=true` 才注册，且主服务仍强制字面量回环地址。`/debug/runtime` 只返回 runtime 与 `database/sql` 聚合计数；pprof 默认关闭，不包含请求正文、Token 或 SQL 参数。

## 可复现命令

```powershell
# 在自己克隆的 order-api 仓库根目录执行，不依赖作者本机目录。

# 下载到 .tmp 并核对固定 SHA-256；不全局安装。
.\scripts\install-k6-local.ps1

# 首次或显式重置前，保证上一次性能服务已经停止。
.\scripts\performance-start.ps1 -ResetData

# 先做一个请求的冒烟；也可选其他 workload 名称。
.\scripts\run-performance.ps1 -Scenario products-list-hot `
  -Model shared-iterations -VUs 1 -Iterations 1 -Duration 1s -RunID smoke-manual

# 执行有界基线：固定 VU 1/5/10/20，以及主要场景各三轮。
.\scripts\run-performance-baseline.ps1
.\scripts\summarize-performance.ps1
.\scripts\analyze-performance-database.ps1

# 结束服务；-StopDatabase 只停止性能容器，保留独立 Volume。
.\scripts\performance-stop.ps1 -StopDatabase
```

单场景入口强制最多 25 VU、200 次/秒、60 秒，HTTP 超时 3 秒。固定 VU 模型默认每次迭代休眠 100 ms，使每 VU 理论上限约 10 次/秒；固定到达率模型将请求速率作为目标并限制最大 25 VU。二者含义不同，不能直接把闭环和开环数字混为服务容量。

种子重置会删除精确性能库中的合成行，必须在无负载时手动执行：

```powershell
.\scripts\performance-reset.ps1
```

脚本不会删除数据库、容器 Volume、开发数据或非性能库。不要并发运行 reset 与 k6。

## 正确性验收

- 普通创建三轮分别新增 101、100、100 个订单；订单项同数，库存分别减少相同数量，没有幂等重放。
- 库存竞争每轮正好创建 100 单、库存减少 100，另外 100 请求得到 `insufficient_stock`；库存从未为负。
- 并发幂等每轮只有 1 个新订单和 1 次库存扣减，另外 19 响应带重放语义；数据库用户级幂等重复组为 0。
- 额外以 25 个不同用户并发使用同一键：25 个请求成功，数据库有 25 个不同 user_id 和 25 个不同订单 ID，库存减少 25，不跨用户复用结果。
- 取消每轮处理 200 个不同订单，状态变化 200、库存回补 200，没有用同一已取消订单的无限重放制造吞吐。
- 每轮后均查询真实数据库：金额与明细汇总一致、无无明细订单、无孤立明细、无负库存、无用户内重复幂等订单。
- 最终隔离库只读验证：1000 商品、25 用户/Session、525 个订单/明细，全部一致性计数为 0，`valid=true`。

## Go 与 MySQL 资源

31 个正式轮次共采集 85 个资源快照。观测到的上界为：服务进程工作集 84 MiB、Go heap alloc 3.745 MiB、87 goroutine；数据库池最多打开/使用 20/20（上限 25），所有轮次池等待增量为 0。累计观测到 184 次 GC，暂停合计 25.6952 ms。服务进程最高占整机 16 逻辑处理器的 1.862%，该归一化值约等于 0.30 个逻辑核；它不是单核 CPU 百分比。

MySQL 85 个样本平均内存约 492.58 MiB、最高 511 MiB；最高 CPU 50.42% 出现在库存竞争。资源轮询粒度可能遗漏很短的峰值，因此这些是观测上界，不是严格资源峰值。

商品列表 50/s 轮次采集了 5 秒 CPU profile，总 CPU 样本仅 120 ms（占墙钟 2.4%）。样本中 `runtime.cgocall` 70 ms，`database/sql.Rows` 关闭/读取累计路径较突出，但总样本只有 12 个 10 ms tick，不足以据此优化函数。Windows Go 工具链缺少 `go tool pprof`，最终用无网络、只读挂载的固定官方 Go 容器解析；前两次分别因只读缓存和 128 MiB tmpfs 太小失败，第三次用 1 GiB tmpfs、2 GiB 容器内存和 `GOMAXPROCS=2` 成功。

## 失败与修正记录

最初的并发幂等脚本错误地让相同键携带不同商品，服务正确返回 19 个 `idempotency_conflict`，k6 因 95% 业务错误以退出码 99 失败。修正为固定商品后重新重置数据并执行三轮，均得到 1 创建、19 重放。该失败证明阈值能够区分合法重放与冲突，没有被计入正式结果。

批量执行受宿主命令会话时限中断过两次，已完成结果文件保持有效；缺失轮次随后逐项补跑。订单创建第 3 轮曾在中断前留下 4 个请求，复用 RunID 会出现 4 次重放；识别出订单增量与响应数不一致后重置性能库并重新采集，正式数据为 100 请求、100 新订单、0 重放。

## 结论与边界

当前基线最明确的瓶颈是单库存行竞争与事务提交，而不是商品查询或连接池。没有证据支持现在引入 Redis：查询在本机 50/s 与最高约 189/s 渐进负载下仍很低，缓存会增加失效与一致性复杂度；库存正确性仍必须由 MySQL 事务保证。现有核心 SQL 都使用主键或唯一索引，也没有证据要求新增索引。数据库证据见 [数据库性能分析](database-performance-analysis.md)。

下一轮应保持同一脚本和种子，先延长单轮时间并在获准后逐步提高到达率，以寻找饱和点；再对明确热点做单变量优化。不能把本轮本机数字与未来不同硬件、网络或数据规模直接比较。
